# 现有 PPT 美化规范

> 本规范适用于输入为现有 PPTX、目标是输出美化版 PPTX 的场景。核心原则：**保持内容和结构不变，只提升视觉。**

## 适用场景

- 用户说"帮我把这个 PPT 做得更美一点""重做一下这个 PPT""美化一下"
- 用户提供一个现有 PPTX 文件作为输入
- 用户明确要求"保持原有风格"或"保持原有页面内容"

## 不适用场景

- 用户要修改 PPT 的内容结构（增删页、调整逻辑）→ 按从文章新建流程处理
- 用户要修改个别文字或数据 → 用演示文稿编辑流程，不需要整页重生
- 扫描版/图片版 PPT 无法提取文字 → 停止并说明需要文字稿

## 核心约束

### 必须保持

1. **页数不变**：原 PPT 多少页，美化版就多少页，不得拆页或合并
2. **页面结构不变**：每页的叙事任务、标题层级、核心结论保持原样
3. **核心内容不变**：标题、关键数据、重要引语不得遗漏或改写
4. **原文锚点**：每页 sourceAnchors 写为「原PPT第N页」

### 可以改变

1. **视觉风格**：配色、插画语言、排版布局、字体气质
2. **文字精简**：原 PPT 文字过多时，精简到 full-image 可承载范围（30-70 字），但核心信息不丢
3. **构图优化**：根据页面任务调整构图，避免每页都是同一个布局

## 工作流程

### 步骤 1：解析原 PPT

使用 `scripts/extract_pptx.mjs` 解析：

```bash
node scripts/extract_pptx.mjs <原PPT.pptx> <输出目录>/source-extracted
```

输出内容：
- `page-01.txt`、`page-02.txt`……每页文字（按出现顺序）
- `original-style.txt` 原 PPT 配色、字体、图片素材摘要
- `outline.txt` 内容大纲表格
- `source_images/` 原 PPT 中的图片素材

解析后必须逐页阅读提取的文字，确认内容完整。如果某页文字提取异常（乱码、缺失），手动从 PPT 中补充。

### 步骤 2：内容规划

基于提取的文字，建立每页的内容记录：

```yaml
page: 3
page_type: example
mode: full-image
title_exact: 家长踩过的坑
takeaway: 学了一堆方法，一遇问题全乱了
visible_copy:
  - 明明学过「共情」「好好沟通」
  - 一看孩子玩手机，瞬间火冒三丈
source_anchors:
  - 原PPT第3页
coverage_ids:
  - CLM-03
visual_idea: 焦虑家长抱头面对成堆书本
```

文字精简规则：
- 原 PPT 正文超过 70 字时，提炼核心要点，保留标题和关键数据
- 精简后的文字必须能回到原 PPT 对应内容，不得新增无来源信息
- 如果某页文字实在无法精简到 full-image 范围，先尝试拆分布局（左右分栏、上下分区），继续精简文字，不得改用其他模式

### 步骤 3：风格锁定

三条路径，按用户意图选择：

#### 路径 A：保持原风格

用户说"保持原有风格""参考这个封面的图片"时：
1. 从 `original-style.txt` 提取配色和字体
2. 从 `source_images/` 中找到代表性插画（通常是封面或内容页主图）
3. 用代表性插画作为 style-master 的参考
4. 提示词中明确描述原风格的视觉特征（配色、插画语言、材质）

#### 路径 B：换全新风格

用户说"做得更美一点""换个风格"时：
1. 按正常流程从风格目录推荐 2-3 个候选
2. 用同一张代表页生成样张
3. 用户选择后锁定

#### 路径 C：用户给参考图

用户提供参考图片时：
1. 直接以参考图为 style-master
2. 提示词中描述参考图的视觉特征

锁定后保存 `style-master.png`，后续每页都附带它作为视觉约束。

### 步骤 4：编写提示词

全部使用 full-image 模式。每页提示词结构：

```text
风格锁定（引用 style-master 的视觉特征）
+ 页面任务（本页要让观众理解什么）
+ 准确文案（从原PPT提取，文字加引号）
+ 构图要求（根据页面任务设计）
+ 输出要求（16:9，原生输出不裁切）
+ 禁止项（不增字、不漏字、不改字、无水印、无商标）
```

文字处理要点：
- 所有可见文字必须逐字列出，用「」或引号标注
- 声明"画面只允许出现以下中文，不增字、不漏字、不改字"
- 原 PPT 中的数据、日期、引语必须准确，不得改写
- 如果原 PPT 有特殊符号（→、·、数字编号），在提示词中明确说明

### 步骤 5：生成代表页

选一张内容丰富的正文页（不是封面）生成代表页，检验：
- 原 PPT 的核心内容是否完整呈现
- 文字是否准确无错误
- 风格是否与 style-master 一致
- 信息密度是否合适

用户确认后锁定，批量生成其余页面。

### 步骤 6：批量生成与质检

使用 `scripts/generate_image.mjs` 生成，脚本内置网络重试。

每页质检清单（必须逐项检查）：

- [ ] **内容完整性**：与原 PPT 提取文字对比，标题、核心结论、关键数据无遗漏
- [ ] **文字准确性**：无错别字、无乱码、无 AI 自行添加的文字
- [ ] **无裁切**：顶部标题不贴边、底部金句完整，原生 16:9 输出
- [ ] **风格一致**：与 style-master 配色、插画语言、材质一致
- [ ] **构图不重复**：避免每页都是左右分栏或居中布局
- [ ] **无多余元素**：无水印、商标、无关人物、敏感信息

失败页最多重试 2 次，每次只修一个明确问题。

### 步骤 7：组装与交付

使用 `scripts/build_ppt.mjs` 组装：

```bash
node scripts/build_ppt.mjs deck-manifest.json output.pptx montage.webp
```

交付物：
- 美化版 PPTX
- 整套缩略图
- 页面图片（按页码排列）
- 提示词汇总
- `source-extracted/` 目录（原 PPT 提取内容）
- 质检记录

## 常见避坑

### 坑 1：用错误的 API 端点

KIE 有多个图像 API，必须用 `gpt-image-2-text-to-image`（支持原生 16:9），不要用 `gpt4o-image`（只支持 1:1/3:2/2:3，需要裁切）。

正确端点：`POST /api/v1/jobs/createTask`，body: `{"model":"gpt-image-2-text-to-image","input":{"prompt":"...","aspect_ratio":"16:9"}}`

### 坑 2：因为文字多就放弃 full-image

不要因为"文字看起来多"就放弃 full-image 模式。GPT Image 2 可以处理 70 字以内的 full-image 页面。文字过多时先精简文字、拆分布局，调整提示词后重试，不得改用其他模式。

### 坑 3：批量生成后不逐页检查

必须逐页检查文字准确性和裁切问题，不能生成完直接组装。之前的教训：9 页顶部标题被裁切、2 页底部金句被裁切，都是因为没有逐页检查。

### 坑 4：提示词用结构化参数清单

GPT Image 2 偏好自然连贯的中文描述，不要用"风格：xxx，配色：xxx，构图：xxx"这种结构化参数清单。要用自然语言分段描述。

### 坑 5：忽略原 PPT 的风格参考

用户说"保持原有风格"时，必须从原 PPT 提取配色和插画语言，不能自己选一个风格。原 PPT 中的封面主图通常是最好的风格参考。

## 验证清单（交付前）

- [ ] 美化版页数 = 原 PPT 页数
- [ ] 每页都有完整文字（无空白页、无只有框架没文字的页）
- [ ] 全部页面为 full-image 模式
- [ ] 原生 16:9 输出，无裁切
- [ ] 风格与 style-master 一致
- [ ] 缩略图总览叙事连贯、风格统一
- [ ] PPTX 文件可正常打开
